# knct-signa 初版設計

## 目的と合意した要件

部内向けの軽量なデジタルサイネージを作る。同じサーバーマシンでBunを起動し、そのマシンのブラウザーでローカルURLを開いて表示する。

- `/kiosk`：表示専用のサイネージ画面。
- `/manage`：Basic認証で保護した管理画面。
- 時計、今日の天気、管理画面で設定したRSSを表示する。
- 外部データソースを追加して表示内容を拡張できる。
- 設定変更と取得データの更新を、ページ再読み込みなしで反映する。
- 実行基盤、依存管理、開発・ビルドコマンドはBunに統一する。
- 設定はJSONファイルに保存し、同時更新はアプリケーションで制御する。
- 管理用のユーザー名・パスワードは`.env`で指定する。

参考は `../Hiroba-news-smart-monitor`。時計・天気・RSSの情報配置、サーバー側の取得とキャッシュを参考にする。参考実装本体はDBを使わず、環境変数と`.env`で設定する。時間割・画像の別サーバーは本プロジェクトの依存にしない。

## 採用技術

| 役割 | 選定 |
| --- | --- |
| 実行基盤・パッケージ管理 | Bun |
| HTTPサーバー | `Bun.serve` |
| ルーティング・Basic認証 | Hono |
| フロントエンド | Vue 3、TypeScript、Composition API、Single-File Components |
| フロントエンド開発・ビルド | Vite、Vue公式プラグイン。CLIはBunで実行する |
| リアルタイム配信 | BunのWebSocket |
| 永続化 | `data/config.json` |
| サーバーのテスト | `bun:test` |

本番はViteの生成済みファイルを同じBunサーバーから配信し、1プロセスで運用する。開発中のみViteを追加起動し、HTTP APIとWebSocketをBunサーバーへプロキシする。キオスクと管理画面は別のHTMLエントリーとVueアプリに分ける。

## 初版の範囲

### キオスク

- 大きな時計、日付、設定した地域名を表示する。時計はブラウザー内で毎秒更新する。
- 今日の天気、現在の気温、最高・最低気温、降水確率を表示する。
- RSSの見出しを配信元付きで表示する。複数フィードと自動送りに対応する。
- 追加データをタイトル・本文のカードとして表示する。
- 横長モニターを主対象とし、画面サイズに応じて配置を調整する。
- 表示内容が多いときは自動送り・ページ切り替えで閲覧できるようにする。
- 接続が切れても取得済みの表示を維持し、再接続中の状態を控えめに表示する。

### 管理画面

- 表示タイトル、天気の地域名・緯度・経度、タイムゾーンを設定する。
- RSSの名前・URL、汎用JSON APIの接続先・表示マッピングを追加・編集・削除する。
- 表示順、有効・無効、取得間隔を設定する。
- 保存結果、入力エラー、取得状態、最終取得日時を確認できる。
- キオスクを開くリンクを用意する。
- 保存競合時は未保存の入力を維持し、最新設定の再取得を案内する。

### データソース

- 天気は参考実装と同じOpen-Meteoを使用する。
- RSS 2.0、Atom、参考実装のフィードに含まれるRSS 1.0/RDFを対象とする。XMLパーサーを使って解析する。
- 汎用JSON APIはHTTP GETで取得し、配列の位置と各要素のタイトル・本文・リンクに対応するプロパティパスを設定する。パスはプロパティ参照として実装する。
- API用の任意ヘッダーは管理設定として保存し、管理APIでのみ扱う。
- 独自形式への拡張は、サーバー側にTypeScriptのアダプターを追加する方式とする。
- 画面からのJavaScript入力、`eval`、シェルコマンドによるデータ変換は提供しない。

初版では画像アップロード、自由配置エディター、複数モニターの個別設定、ユーザー管理、過去データの蓄積は実装範囲に含めない。

## コンポーネントと責務

- **ConfigStore**：設定の読み込み、検証、更新キュー、revision照合、ファイル保存を担当する。
- **DataSourceAdapter**：各配信元を共通の表示データに変換する。HTTPやVueの状態には依存しない。
- **SourceScheduler**：取得間隔、タイムアウト、同時取得の制限、キャッシュ、再取得を担当する。
- **DisplayService**：表示用設定と最新データを組み立て、更新ごとに配信用の状態を作る。接続先ヘッダー等を除外する。
- **HTTP routes**：画面配信、管理認証、設定API、表示APIを担当する。
- **RealtimeHub**：表示状態のWebSocket配信、接続・切断の後始末を担当する。
- **Vueアプリ**：表示・入力と受信状態を担当する。外部データの取得はサーバー経由とする。

## URLと認証

| URL | 用途 | Basic認証 |
| --- | --- | --- |
| `/` | `/kiosk`へリダイレクト | なし |
| `/kiosk` | キオスク画面 | なし |
| `/manage`、`/manage/*` | 管理画面 | 必須 |
| `GET /api/manage/config` | 管理設定取得 | 必須 |
| `PUT /api/manage/config` | 設定更新 | 必須 |
| `GET /api/manage/status` | 取得状態の確認 | 必須 |
| `GET /api/display` | 公開用の表示状態 | なし |
| `/ws` | 表示状態の配信 | なし |

WebSocketは表示状態の購読専用とし、設定変更を受け付けない。キオスクへの配信にはBasic認証の資格情報、API用ヘッダー、管理専用設定を含めない。

管理設定の変更は同一オリジンのJSONリクエストとして受け付ける。WebSocketの接続時も同一オリジンを確認する。外部データはVueの通常のテキスト描画を使い、外部のHTMLをそのまま挿入しない。データ取得先・リンクはHTTP/HTTPSに限定する。

セキュリティは部内向けの小さな構成とし、独自のログイン画面や権限管理は追加しない。Basic認証自体は通信を暗号化しないため、localhost以外へ公開する際のHTTPS終端は運用側で選択する。

## 環境変数と初期値

- `HOST`：既定は`127.0.0.1`。部内の他端末から管理する場合は明示的に変更する。
- `PORT`：既定は`3000`。
- `MANAGE_USERNAME`、`MANAGE_PASSWORD`：両方必須。空値・未設定は起動エラーとし、認証なしへのフォールバックは行わない。
- `CONFIG_PATH`：既定は`data/config.json`。

`.env`はGitの追跡対象外とし、資格情報の値はブラウザー向けコード、レスポンス、ログに出さない。`.env.example`には項目名と入力用の例を用意する。

設定の初期値はタイトル`knct-signa`、タイムゾーン`Asia/Tokyo`、地域は参考実装と同じ高松（緯度34.3401、経度134.0434）とする。天気の取得間隔は10分、RSS・JSON APIは5分を既定とする。RSS・JSON APIは管理画面から登録し、初期状態では空にする。

## JSON設定と同時更新

設定には`schemaVersion`、`revision`、表示設定、天気設定、データソース一覧を含める。`schemaVersion`は1から開始し、`revision`は保存成功ごとに増加する。データソースには安定したIDを割り当てる。登録は最大32件、取得間隔は60秒から24時間の整数秒とする。

サーバーが唯一の書き込み主体になる。実行中のファイル直接編集や複数サーバープロセスからの共有書き込みは対応範囲外とする。

設定更新は次の全体を単一のキュー内で実行する。

1. クライアントの`revision`と現在値を比較する。不一致は`409 Conflict`。
2. 入力の型、URL、緯度経度、更新間隔、データソースID等を検証する。不正な値は`400`。
3. 現在設定を書き換えず、次の設定オブジェクトを作る。
4. 同じディレクトリに一意な一時ファイルを作成し、JSONを完全に書き込む。
5. `rename`で設定ファイルを置き換える。
6. メモリ上の設定を切り替え、スケジューラーへ反映し、表示状態を配信する。

手順5までの保存失敗はサーバーエラーとし、現在のメモリ設定を維持する。失敗でキューが停止しないようにし、一時ファイルは後始末する。設定の保存成功と外部データ取得の成功は別に扱い、保存時に外部APIの応答を待たない。

設定ファイルが存在しない場合だけ初期設定を作成する。不正なJSON、検証エラー、未対応の`schemaVersion`では既存ファイルを上書きせず、起動時に理由を知らせる。原子的な置換は保存途中の読み込みを防ぐためのものであり、電源断時の直前の保存の永続性保証までは初版の要件にしない。

## 外部データの取得と障害時動作

- 起動後と有効なソースの設定変更後に取得し、その後は設定間隔で更新する。
- 同じソースの取得を重ねず、全体の同時取得数は最大4件とする。
- HTTP取得は10秒でタイムアウトし、応答サイズは展開後2MiBまで、RSS・JSONの表示件数はソースごとに最大100件とする。
- 最終成功データとその取得日時、最終試行の状態をメモリに保持する。
- 一部ソースの取得失敗で他のソースの取得・表示を停止しない。
- 失敗時は最終成功データを維持して古いデータであることを示す。初回取得に失敗した場合は取得できない状態を表示する。
- ソースの接続設定が変わった場合は対応するキャッシュを無効にして再取得する。古い取得処理を破棄または世代照合で無効にし、変更前の応答で新しいデータを上書きしない。
- 天気・RSS・JSON APIのリアルタイム性は取得頻度に依存する。取得後の画面反映をWebSocketで即時化する。

## WebSocketの状態同期

初版では表示データが小さいことを前提に、差分適用の代わりに完全な表示スナップショットを配信する。接続時も同じ形式で最新状態を送る。

メッセージには種別、サーバー起動ごとの識別子、状態の連番、設定の`revision`、表示用設定、ソース別のデータと取得状態を含める。サーバー再起動後は新しい識別子で状態を受け入れる。

ブラウザーは切断時に表示を維持し、上限付きの待機時間とジッターで再接続する。再接続時には完全な状態を受信して同期する。サーバー側のpingと切断後の後始末を行い、送信が滞る接続は切断して再同期に任せる。

管理APIの設定更新応答にも新しい`revision`を返す。管理画面の編集中の入力は、配信された設定で勝手に上書きしない。

## 検証と完了条件

- Bunで依存のインストール、Vueのビルド、サーバー起動、テストが実行できる。
- `/kiosk`は認証なしで表示でき、時計が毎秒更新される。
- `/manage`とすべての管理APIは未認証・誤資格情報で`401`、正しい資格情報で利用できる。
- 資格情報が未設定の場合は起動できず、公開API・WebSocket・配信ファイルに秘密情報が含まれない。
- 設定を保存し、サーバーを再起動しても復元できる。
- 同じ`revision`による同時更新では1件だけ保存され、もう1件は`409`になる。
- 保存失敗時は元の設定が維持され、その後の保存が可能である。
- RSS・Atom・RDFと汎用JSON APIを固定データで検証し、タイムアウト・不正応答・古い取得結果の到着を確認する。
- 開いているキオスクに設定変更と取得結果が反映され、WebSocket再接続後に最新状態へ戻る。
- ブラウザーで両画面のレイアウト、入力・保存、空状態、取得失敗時の表示を確認する。
